1. DB INDEXING + SCHEMA TUNING

* Do NOT drop tables or overwrite existing records.
* Use migration-safe changes only.
* Preserve all existing users, balances, tasks, transactions, notifications, support messages, admin settings, branding, and preferences.

* Normalize repeated data where safe.

* Keep task/assignment state separate from history.

=================================

* Do NOT rely on memory-only state for critical data.

* Minimize startup work.
* Do not preload large datasets at boot unless required.
* Lazy-load non-critical modules.
* Initialize only what is needed for the app to respond quickly.

* Remove unnecessary dependencies if safe.
* Split heavy frontend code into lazy-loaded chunks.
* Compress and optimize static assets.
* Use caching headers where appropriate for static resources.
* Keep bundle size small.
* Avoid repeated expensive computations on page load.

* Add health check endpoint.
* Ensure server can restart without data loss.
* Make startup idempotent.
* Do not re-seed or reinitialize existing DB data on every deploy.

Replit-specific behavior:

* Keep the project runnable in a single deployment environment.
* Use clear start commands.
* Make sure the app can boot reliably after refresh or redeploy.
* Ensure logs are readable for debugging.
* Keep environment config separate from code.
* Make sure persistent data survives Replit restarts through the database, not local memory.

Low-bandwidth optimization:

* Paginate long lists.
* Use skeleton loaders instead of blocking screens.
* Lazy-load heavy UI sections like analytics, transactions, activity, and product lists.
* Avoid full page reloads.
* Keep initial screen responsive first, then load secondary content.

Safety rules:
